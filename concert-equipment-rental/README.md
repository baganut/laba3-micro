# Concert Equipment Rental — лабораторная работа №3

**Тема:** декомпозиция и проектирование микросервисной системы аренды концертного оборудования.  
**Статус:** проектная спецификация; реализация на Java/Spring Boot планируется в следующих лабораторных.

## 1. Описание предметной области

Система Concert Equipment Rental предназначена для аренды профессионального оборудования для концертов, фестивалей, корпоративных и иных мероприятий. В каталоге представлены свет, звук, экраны, спецэффекты и сценический конструктив. Клиент выбирает оборудование, указывает даты и адрес мероприятия, проверяет доступность, оформляет заказ и оплачивает аренду. Система резервирует конкретные единицы оборудования, организует доставку/монтаж, а после мероприятия — демонтаж и возврат. Администраторы управляют каталогом и складскими единицами, а сотрудники логистики исполняют задания по доставке и возврату.

### Акторы и внешние системы

| Актор / система | Роль |
|---|---|
| Клиент (организатор мероприятия) | Просматривает каталог, проверяет доступность, оформляет и оплачивает аренду, отслеживает заказ |
| Администратор каталога | Создаёт категории и карточки оборудования, меняет характеристики и базовые тарифы |
| Складской сотрудник | Учитывает физические единицы, подтверждает выдачу, приём и техническое состояние |
| Логист / монтажная бригада | Выполняет доставку, монтаж, демонтаж и возврат |
| Keycloak | Внешний провайдер OAuth 2.0 / OpenID Connect, выдаёт JWT |
| Платёжный провайдер | Принимает оплату и инициирует возврат; интеграция представлена адаптером payment-service |
| Email/SMS-провайдер | Внешняя доставка уведомлений |

### Пользовательские сценарии

1. Как клиент, я хочу просматривать оборудование по категориям и характеристикам, чтобы подобрать комплект для мероприятия.
2. Как клиент, я хочу указать период аренды и получить доступные позиции, чтобы не заказать уже занятое оборудование.
3. Как клиент, я хочу сформировать заказ из нескольких категорий оборудования, чтобы оформить аренду одним обращением.
4. Как клиент, я хочу оплатить заказ онлайн, чтобы подтвердить бронирование.
5. Как клиент, я хочу указать адрес и временное окно доставки, чтобы получить оборудование к началу мероприятия.
6. Как клиент, я хочу отслеживать статусы заказа и логистики, чтобы понимать, когда оборудование будет доставлено и забрано.
7. Как складской сотрудник, я хочу отмечать выдачу и возврат каждой единицы, чтобы поддерживать достоверные складские остатки.
8. Как администратор, я хочу менять карточки оборудования и тарифы, чтобы поддерживать актуальность каталога.

## 2. Доменные события и ограниченные контексты

### Доменные события (прошедшее время)

`EquipmentCreated`, `EquipmentUpdated`, `AvailabilityChecked`, `StockUnitReserved`, `StockReservationRejected`, `BookingCreated`, `BookingConfirmed`, `BookingCancelled`, `BookingExpired`, `PaymentRequested`, `PaymentCompleted`, `PaymentFailed`, `RefundRequested`, `RefundCompleted`, `DeliveryScheduled`, `EquipmentDispatched`, `EquipmentDelivered`, `InstallationCompleted`, `DismantlingCompleted`, `EquipmentReturned`, `ReturnInspectionFailed`, `NotificationSent`.

### Ограниченные контексты и глоссарии

| Контекст | Термины контекста |
|---|---|
| Каталог (catalog) | **Карточка оборудования** — описание модели/типа; **категория** — свет/звук/экраны/спецэффекты/конструктив; **тариф** — базовая цена аренды за единицу времени; **характеристика** — технический параметр позиции |
| Склад и доступность (inventory) | **Складская единица** — конкретный физический экземпляр; **период занятости** — интервал, когда единица недоступна; **резерв** — временная блокировка единицы; **состояние** — технический статус единицы |
| Аренда (booking) | **Заказ** — агрегат намерения клиента арендовать набор позиций; **строка заказа** — количество и период для типа оборудования; **сумма заказа** — рассчитанная стоимость; **статус** — этап жизненного цикла заказа |
| Платежи (payment) | **Платёж** — попытка получить деньги за заказ; **транзакция провайдера** — внешний идентификатор операции; **возврат** — обратная финансовая операция; **ключ идемпотентности** — идентификатор повторяемого запроса |
| Логистика (logistics) | **Задание** — работа по адресу и временному окну; **рейс** — доставка/забор; **монтаж** — подготовка оборудования на площадке; **акт возврата** — результат приёмки и осмотра |
| Уведомления (notification) | **Шаблон** — формат сообщения; **получатель** — адрес email или телефон; **попытка отправки** — отдельное выполнение доставки; **статус доставки** — результат провайдера |

Один и тот же `bookingId` в разных контекстах является идентификатором-ссылкой, а не общей разделяемой сущностью. Каждый сервис хранит собственную модель и является владельцем только своих данных.

## 3. Сервисы и границы ответственности

В системе 6 бизнес-сервисов (требование — от 4 до 7). Gateway, Keycloak и инфраструктура в это число не входят.

### 3.1 `catalog-service`

- **Ответственность:** управление каталогом типов оборудования, категориями, техническими характеристиками и базовыми тарифами; предоставление поискового API.
- **Владеет данными:** `EquipmentProduct`, `Category`, `Specification`, `RentalRate`.
- **API / события:** `GET /api/v1/equipment`, `GET /api/v1/equipment/{id}`, административные `POST/PATCH`; публикует `catalog.equipment-created`, `catalog.equipment-updated`.
- **Зависит от:** не вызывает другие бизнес-сервисы; публикует события в RabbitMQ.
- **НФТ:** преимущественно чтение, ориентир 100–300 RPS в пике; p95 чтения до 300 мс; каталог доступен независимо от платёжного и логистического контуров.
- **Почему отдельный:** каталог имеет самостоятельный жизненный цикл, высокую частоту чтения и требования к поиску/кэшированию; изменения описания не должны менять складские резервы.

### 3.2 `inventory-service`

- **Ответственность:** учёт конкретных физических единиц оборудования, проверка доступности на интервал и атомарное резервирование/освобождение.
- **Владеет данными:** `StockUnit`, `Reservation`, `AvailabilityWindow`, `Inspection`.
- **API / события:** внутренние `GET /internal/v1/availability`, `POST /internal/v1/reservations`, `DELETE /internal/v1/reservations/{id}`; публикует `inventory.reservation-created`, `inventory.reservation-rejected`, `inventory.reservation-released`.
- **Зависит от:** подписан на изменения каталога; вызывается booking-service и logistics-service.
- **НФТ:** критичны конкурентный доступ и отсутствие двойного резервирования; транзакционная запись; p95 проверки до 500 мс.
- **Почему отдельный:** владение физическими единицами и блокировками отличается от описания товаров; здесь сосредоточена логика пересечения временных интервалов и конкуренции.

### 3.3 `booking-service`

- **Ответственность:** оформление аренды, расчёт снимка стоимости заказа, управление статусами и оркестрация саги оформления.
- **Владеет данными:** `Booking`, `BookingLine`, `BookingStatusHistory`, `SagaState`, `ProcessedEvent`.
- **API / события:** публичные `POST /api/v1/bookings`, `GET /api/v1/bookings/{id}`; внутренний `PATCH /internal/v1/bookings/{id}/payment-status`; публикует `booking.created`, `booking.confirmed`, `booking.cancelled`, `booking.expired`.
- **Зависит от:** синхронно вызывает catalog-service для проверки карточек/тарифов и inventory-service для резерва; создаёт платёж через payment-service; подписан на результаты платежа и резерва.
- **НФТ:** критичный бизнес-процесс; p95 создания заказа без внешнего провайдера до 2 с; идемпотентность и восстановление саги обязательны.
- **Почему отдельный:** заказ — самостоятельный агрегат с собственным жизненным циклом; его нельзя смешивать с физическим учётом или финансовыми транзакциями.

### 3.4 `payment-service`

- **Ответственность:** создание платежей, обработка callback от платёжного провайдера, проведение возвратов и аудит финансовых операций.
- **Владеет данными:** `Payment`, `Refund`, `ProviderCallback`, `PaymentAttempt`.
- **API / события:** внутренние `POST /internal/v1/payments`, `POST /internal/v1/refunds`; внешний callback `POST /api/v1/payments/provider-callback`; публикует `payment.completed`, `payment.failed`, `payment.refunded`.
- **Зависит от:** внешний платёжный провайдер; публикует события для booking-service и notification-service.
- **НФТ:** финансовая целостность и аудит важнее пропускной способности; обязательны подпись callback, идемпотентность, сверка статусов.
- **Почему отдельный:** отдельные секреты, интеграция с провайдером, требования к аудиту и жизненный цикл возврата.

### 3.5 `logistics-service`

- **Ответственность:** планирование доставки и забора, назначение бригад, фиксация монтажа/демонтажа и результата возвратной приёмки.
- **Владеет данными:** `LogisticsTask`, `DeliveryWindow`, `CrewAssignment`, `HandoverAct`.
- **API / события:** `GET /api/v1/logistics/tasks/{id}`, внутренний `POST /internal/v1/logistics/tasks`; публикует `logistics.delivery-scheduled`, `logistics.equipment-delivered`, `logistics.equipment-returned`, `logistics.return-inspection-failed`.
- **Зависит от:** подписан на `booking.confirmed`; вызывает inventory-service при фиксации возврата/осмотра.
- **НФТ:** нагрузка умеренная, но важны надёжность расписания и аудит действий; p95 чтения статуса до 500 мс.
- **Почему отдельный:** география, расписание бригад и исполнение работ имеют иную модель и могут развиваться независимо от оформления заказа.

### 3.6 `notification-service`

- **Ответственность:** отправка транзакционных email/SMS о статусах заказа, оплате, доставке и возврате.
- **Владеет данными:** `Notification`, `DeliveryAttempt`, `Template`.
- **API / события:** внутренний `POST /internal/v1/notifications`; подписан на события booking/payment/logistics; публикует `notification.sent`, `notification.failed`.
- **Зависит от:** RabbitMQ и внешние email/SMS-провайдеры; не находится в критическом синхронном пути оформления заказа.
- **НФТ:** допускается задержка уведомления до нескольких минут; повторные попытки с backoff и DLQ; отправка должна быть идемпотентной по `eventId + channel`.
- **Почему отдельный:** сбой провайдера уведомлений не должен блокировать аренду; шаблоны и каналы меняются независимо от бизнес-транзакций.

### Альтернативное разбиение, от которого отказались

Рассматривали вариант из трёх крупных сервисов: `product-service` (каталог + склад), `order-service` (заказы + платежи) и `operations-service` (логистика + уведомления). Отказались от него по следующим причинам:

1. Каталог описывает тип оборудования, а склад — конкретные физические экземпляры и временные блокировки; у них разная нагрузка и разные правила согласованности.
2. Платежи требуют отдельного аудита, идемпотентности и интеграции с внешним финансовым провайдером.
3. Логистика имеет самостоятельный жизненный цикл и может быть недоступна без остановки оформления заказа.
4. Уведомления — некритичный побочный процесс, поэтому их нельзя помещать в тот же отказный контур, что и заказы.

## 4. Инфраструктурное ПО

| Компонент | Кто использует | Обоснование |
|---|---|---|
| PostgreSQL (отдельная БД/схема и отдельный пользователь на сервис) | Все 6 сервисов, но каждая БД принадлежит только одному сервису | Заказы, платежи, резервы и склад требуют транзакций и ограничений целостности. Общие таблицы и прямой доступ к чужой БД запрещены |
| Redis | catalog, inventory | Кэш часто читаемых карточек/фильтров; короткие блокировки при резервировании. Источник истины по резервам — PostgreSQL, Redis не единственное хранилище |
| RabbitMQ | Все сервисы через exchange/queues | Команды и доменные события, маршрутизация по routing key, повторная доставка и DLQ. Для умеренного потока бизнес-событий Kafka избыточна |
| Spring Cloud Gateway | Внешний вход | Единая точка входа, маршрутизация, JWT-проверка через Keycloak, rate limiting; сервисы не публикуют клиентские порты напрямую |
| Keycloak | Gateway и клиент | OAuth 2.0 / OpenID Connect, выдача JWT и роли `CUSTOMER`, `ADMIN`, `WAREHOUSE`, `LOGISTICS` без собственной реализации авторизации |
| MinIO (S3 API) | catalog, logistics | Хранение изображений оборудования, паспортов, актов и документов; бинарные файлы не хранятся в PostgreSQL |
| OpenTelemetry + Prometheus + Grafana | Все сервисы | Корреляция трассировки по `traceId/correlationId`, метрики задержек, ошибок, очередей и состояния саг |
| Docker Compose | Локальная разработка | Воспроизводимый запуск инфраструктуры и сервисов на машине разработчика |

У каждого бизнес-сервиса своя БД: `catalog_db`, `inventory_db`, `booking_db`, `payment_db`, `logistics_db`, `notification_db`. Даже если локально все БД размещены в одном экземпляре PostgreSQL, логические базы, пользователи и права раздельные. Запрещены общие таблицы и межсервисные JOIN.

## 5. Взаимодействия

### Синхронные вызовы (REST)

| № | Инициатор → получатель | Метод и путь | Назначение |
|---|---|---|---|
| 1 | Клиент → Gateway → catalog | GET `/api/v1/equipment?page=0&size=20` | Просмотр каталога |
| 2 | Клиент → Gateway → booking | POST `/api/v1/bookings` | Создание заказа с `Idempotency-Key` |
| 3 | booking → catalog | GET `/internal/v1/equipment/{equipmentId}` | Проверка существования и получение снимка тарифа |
| 4 | booking → inventory | POST `/internal/v1/reservations` | Атомарный резерв единиц на период |
| 5 | booking → payment | POST `/internal/v1/payments` | Создание платежа и получение paymentUrl |
| 6 | logistics → inventory | POST `/internal/v1/stock-units/{id}/inspection` | Обновление состояния после возврата |

Синхронные вызовы имеют таймауты (обычно 1–2 секунды для внутренних запросов), ограниченные повторы только для безопасных/идемпотентных операций и circuit breaker. Повтор POST допускается только с тем же `Idempotency-Key`.

### Асинхронные взаимодействия (RabbitMQ)

| Routing key / очередь | Издатель | Подписчики | Назначение |
|---|---|---|---|
| `booking.created` | booking | notification | Уведомить о принятии заказа в обработку |
| `inventory.reservation-created` | inventory | booking | Резерв подтверждён |
| `inventory.reservation-rejected` | inventory | booking | Недостаточно свободных единиц |
| `payment.completed` | payment | booking, notification | Платёж прошёл |
| `payment.failed` | payment | booking, notification | Платёж отклонён |
| `booking.confirmed` | booking | logistics, notification | Запустить подготовку доставки |
| `booking.cancelled` / `booking.expired` | booking | inventory, notification | Освободить резерв и уведомить клиента |
| `logistics.equipment-delivered` | logistics | notification | Оборудование доставлено |
| `logistics.equipment-returned` | logistics | inventory, notification | Оборудование возвращено |

### Единый конверт события

```json
{
  "eventId": "5d6e3a4a-4a2d-4d7a-9c9f-5d3e4a2b1c00",
  "eventType": "payment.completed",
  "occurredAt": "2026-11-07T08:30:00Z",
  "schemaVersion": 1,
  "correlationId": "a0a1a2a3-a4a5-46a7-8a9a-123456789abc",
  "payload": {
    "bookingId": "b0b1b2b3-b4b5-46b7-8b9b-123456789abc",
    "paymentId": "c0c1c2c3-c4c5-46c7-8c9c-123456789abc",
    "amount": 125000.00,
    "currency": "RUB"
  }
}
```

Обработчики сохраняют `eventId` в таблице `processed_events` в своей БД в одной локальной транзакции с изменением бизнес-состояния. Повторно доставленное событие игнорируется. Для публикации используется Transactional Outbox: запись бизнес-изменения и outbox-события фиксируется в одной транзакции; отдельный publisher отправляет outbox в RabbitMQ. Ошибочные сообщения после ограниченного числа повторов уходят в DLQ.

## 6. Сквозной сценарий и согласованность (Saga)

### Успешный сценарий аренды

1. Клиент через Gateway отправляет `POST /api/v1/bookings` с `Idempotency-Key`, датами и строками заказа.
2. booking-service создаёт заказ `PENDING_RESERVATION` и фиксирует команду саги.
3. booking синхронно запрашивает карточки/тарифы у catalog-service и сохраняет ценовой снимок в заказе.
4. booking вызывает inventory-service для атомарного резерва на период. inventory проверяет пересечение интервалов и доступность конкретных единиц, создаёт резерв с TTL/сроком действия.
5. После подтверждения резерва booking переводит заказ в `PENDING_PAYMENT` и вызывает payment-service.
6. payment-service создаёт платёж у внешнего провайдера и возвращает ссылку на оплату. Клиент оплачивает.
7. Провайдер вызывает callback payment-service. Сервис проверяет подпись, фиксирует платёж и публикует `payment.completed`.
8. booking получает событие, проверяет `eventId` и текущий статус, переводит заказ в `CONFIRMED`, публикует `booking.confirmed`.
9. logistics создаёт задание доставки; notification отправляет подтверждение клиенту.

### Сбой и компенсирующие действия

| Сбой | Реакция / компенсация |
|---|---|
| Каталог недоступен до создания резерва | Заказ остаётся `FAILED`/не создаётся; клиент получает 503/повторяет запрос с тем же ключом. Резерва и платежа ещё нет |
| inventory отклонил резерв (позиция занята) | booking переводит заказ в `REJECTED`; платёж не создаётся; клиенту возвращается 409 с недоступными строками |
| payment-service недоступен после резерва | booking сохраняет `PENDING_PAYMENT`, повторяет команду создания платежа с тем же idempotency key; при истечении окна отменяет заказ и освобождает резерв |
| Платёж отклонён | `payment.failed` → booking переводит заказ в `CANCELLED` и отправляет команду/вызов освобождения резерва; компенсация — `ReleaseReservation` |
| Брокер недоступен после фиксации платежа | событие остаётся в outbox payment; publisher повторяет отправку. Состояние платежа не теряется |
| Событие `payment.completed` пришло дважды | booking проверяет `eventId` в `processed_events`, повторно не подтверждает заказ и не создаёт логистическое задание |
| Платёж успешен, но резерв уже истёк/заказ отменён | booking не подтверждает заказ; публикует `refund.requested`; payment выполняет возврат и публикует `payment.refunded` |
| logistics недоступен после подтверждения заказа | заказ остаётся `CONFIRMED`; событие `booking.confirmed` повторно доставляется, логистическое задание создаётся идемпотентно; уведомление о задержке отправляется отдельно |

Сага реализована как оркестрация в booking-service. Это не распределённая ACID-транзакция: каждый сервис фиксирует собственную локальную транзакцию, а при неуспехе выполняются компенсирующие действия. Для долгих процессов предусмотрен срок резерва, например 30 минут, и фоновая задача истечения.

## 8. Контракты API

Отдельные OpenAPI 3.1 файлы находятся в `api/`:

- [`catalog-service.yaml`](api/catalog-service.yaml)
- [`inventory-service.yaml`](api/inventory-service.yaml)
- [`booking-service.yaml`](api/booking-service.yaml)
- [`payment-service.yaml`](api/payment-service.yaml)
- [`logistics-service.yaml`](api/logistics-service.yaml)
- [`notification-service.yaml`](api/notification-service.yaml)

Во всех контрактах используется единая ошибка `Problem` (`application/problem+json`) с полями `type`, `title`, `status`, `detail`, `instance`, `traceId`. Создание заказа и платежа требуют `Idempotency-Key`. Списки используют `page` и `size`. Внутренние операции помечены тегом `internal`.

Проверка OpenAPI локально (Node.js установлен):

```bash
npx @redocly/cli lint api/*.yaml
```

Открыть каждый YAML можно в https://editor.swagger.io/ (File → Import file). Внешние эндпоинты помечены `public`, внутренние — `internal`.

## 10. Как загрузить проект на GitHub и сдать преподавателю

### Вариант A — через сайт GitHub

1. Перейди на https://github.com/ и войди в аккаунт.
2. Нажми **New repository**.
3. Название: `concert-equipment-rental`.
4. Выбери **Public** (если преподаватель не требует Private) и нажми **Create repository**. Не добавляй README автоматически, так как он уже есть в проекте.
5. Распакуй ZIP-архив на компьютере.
6. В созданном репозитории нажми **Add file → Upload files**.
7. Перетащи содержимое папки `concert-equipment-rental` (именно файлы и папки внутри, а не ZIP-архив).
8. В поле commit message напиши `Add lab 3 microservices architecture`.
9. Нажми **Commit changes**.
10. Проверь, что на главной странице видны `README.md`, `api/` и `docs/`, а файлы YAML открываются.

### Вариант B — через Git и терминал

Установи Git, открой терминал в распакованной папке и выполни:

```bash
git init
git add .
git commit -m "Add lab 3 microservices architecture"
git branch -M main
git remote add origin https://github.com/ВАШ_ЛОГИН/concert-equipment-rental.git
git push -u origin main
```

Заменить `ВАШ_ЛОГИН` на свой GitHub username. Если GitHub запросит авторизацию, войди через браузер или используй Personal Access Token вместо пароля.
